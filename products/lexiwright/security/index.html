Security and data

Lexiwright runs entirely on Atlassian. The glossary is kept in Forge storage on your site, pages are read and changed as the person using the app, and it makes no calls to outside servers.

Built only on Atlassian Forge

Lexiwright is built only on Atlassian Forge. Its manifest allows no outbound network access and has no remotes, no web triggers and no Connect modules. Its eligibility for Atlassian's Runs on Atlassian program has not been confirmed yet.

Where your data goes

Nowhere outside Atlassian. The app declares no outbound network access, no web triggers, no remotes, no external backend, no analytics, no email and no third-party service. Pages are read through the Confluence REST API as the person using the app, matched against the glossary in memory and not stored. The glossary and the settings are in Forge storage on your site.

Forge storage follows the data residency of the host product (your Confluence or Jira site). Atlassian runs Forge functions on its own infrastructure and aims to run them in the same region.

What is stored

Lexiwright keeps the following in Forge storage on your site. Page text is never stored: it is read in memory to find terms and, when someone links terms, written back to Confluence as a new page version.

DataWhyHow long
Glossary terms: term, synonyms and abbreviations, definition, category, owner (free text, a team or role), link, status, the term to use instead, the case setting, creation and change times. Personal data

None is stored by the app: no account ids, names or email addresses. The account id of the person using the app and, when editing is limited to groups, their group names are used in memory during a request to check what they may do; they are not stored or logged. Editors may type personal data into a definition or the owner field; it is then part of the glossary. Because the app stores no account ids, it has nothing to report to Atlassian's personal data reporting API and requests no scope for it.

Permissions

Every permission the app requests, and why. The scopes are granular unless the table says otherwise.

ScopeWhy the app needs it
storage:app Forge storage on your site for the glossary and the settings
read:page:confluence Read the page someone is viewing, to count and list the glossary terms it uses, and before linking terms in it. The text is not stored
write:page:confluence Save the page with linked terms as a new version, only when a person chooses Link glossary terms and confirms
read:user:confluence Read the group membership of the person using the app, when an administrator limits editing to groups
read:group:confluence List the groups of the site on the settings page, so that an administrator can choose the editor groups

There is no delete scope, no admin scope and no offline user impersonation. Every Confluence request is made as the person using the app, while they use it.

Access control

Every Confluence request is made with the identity of the person using the app, so Confluence decides which pages they may read and change. Every licensed user can read the glossary. Who may add, change, approve and delete terms is set on the settings page (everyone, or chosen groups and Confluence administrators) and checked on the server; when suggestions are on, everybody else can suggest terms for review. Replacing the whole glossary by import is for administrators only. The licence is checked on the server and fails closed in production.

Untrusted input

Terms, definitions and imported CSV files are untrusted input. They are cleaned and limited on the server: up to 3,000 terms, 80 characters per term, 10 synonyms per term and 2,000 characters per definition, and links must start with https:// or http://. Linking changes only plain body text of the page: headings, links, code and other macros are left alone.

Other points

Rovo (optional)

The Glossary agent and the Look up a glossary term action are Atlassian's Rovo features. The action reads only the app's own storage and returns up to three matching approved or deprecated terms (name, synonyms, definition, category, owner and link) to Rovo, which processes them under Atlassian's terms. Suggested terms are never returned. Sites that do not use Rovo are unaffected.

Logging

Unexpected errors only (class and message). The app does not log page text or glossary content.

Encryption

Data in transit and at rest is protected by the Atlassian Forge platform. The app has no database or storage outside Forge.

Sub-processors

None besides Atlassian.

AI and language models

None in the app itself. The optional Rovo agent and action are Atlassian's Rovo features (see above).

Vulnerabilities and incidents

We fix vulnerabilities within the windows Atlassian requires of Marketplace apps (critical: 10 days, high: 4 weeks, medium: 12 weeks, low: 25 weeks) and tell Atlassian about security incidents within 48 hours. Dependencies are checked for known vulnerabilities before each release.

Report a vulnerability to support@karelialabs.com. Please include what you found, how to reproduce it and which app and version are affected, and give us a reasonable time to fix it before you publish details.

Deleting data

Editors delete terms in the glossary, and an administrator can replace the whole glossary by import. Uninstalling the app removes it from your site, and Atlassian then deletes its stored data under its Forge data retention rules. Pages where terms were linked keep the glossary macros, because the pages belong to your Confluence, and the page history keeps the version from before the linking.
